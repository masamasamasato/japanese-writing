# 文書の種類ごとのガイド

共通の原則は `principles.md` にある。ここでは種類ごとに「何を優先するか」「定型の構成」「よくある失敗」をまとめる。ユーザーの依頼に該当する節だけ読めばよい。

## 技術記事（Zenn・Qiita・ブログ）

**読み手**: 検索で流れ着いた、自分と同じ問題を抱えている人。忙しく、記事の冒頭で「読む価値があるか」を判断する。

**文体**: 敬体（です・ます）。常体でも成立するが、敬体のほうが読者層を選ばない。

**構成**

1. 冒頭3行で「誰向けか」「何がわかるか」「前提条件」を書く
2. 目次（長い記事の場合）。見出しは分類ラベルではなく各節の主張にし、目次だけで記事の筋が伝わるようにする
3. 結論または完成形を先に見せる（最終的なコード、動く画面、得られた数値）
4. 手順・解説
5. ハマりどころ・注意点
6. まとめは短く。本文の繰り返しにしない。次に読むべきもの、試すべきことを一言で

**よくある失敗**

- 冒頭が自分語りや経緯の説明で、本題が2画面目以降にある
- 見出しが「はじめに」「環境」「手順」「まとめ」だけで、中身が想像できない
- コードの前後に説明がなく、何を示すコードか読み手が推測する必要がある
- 「〜と思います」「〜かもしれません」が多く、検証済みのことまで自信なさげに見える

**コードと文章の関係**

- コードブロックの直前に「何をするコードか」を一文で書く
- コードの直後に「注目すべき箇所」を書く（全行を説明しない）
- 長いコードは要点だけ抜粋し、全文はリポジトリや折りたたみに置く

## Slack・社内連絡

**読み手**: 通知で流れてくる中で、スマホや作業の合間に読む同僚。読み飛ばされる前提で書く。

**文体**: 敬体。相手やチャンネルの文化に合わせて崩してよい。

**構成**

1. 1行目で用件を言い切る。「〇〇の件、△△をお願いしたいです」「〇〇が完了しました」
2. 相手にしてほしいことと期限（あれば）
3. 背景・補足。長くなるならスレッドに分ける

**よくある失敗**

- 挨拶や前置きで1行目が埋まり、用件がどこにあるかわからない
- 「お手すきの際に」「もしよろしければ」で期限や優先度がぼやける。急ぎならそう書く
- 一つの投稿に複数の依頼が混ざる。別々に投げるか、番号をつける
- 質問と報告が混ざり、返事が必要なのかわからない
- 相手の指摘への個別回答と、まとめ直したスケジュール・一覧で同じ内容を二度書く。一覧を確定版にし、回答側は差分（「前回から変わった点」）だけにする

**社外向けの連絡（メールや Slack コネクト）で守ること**

- 経緯（「以前ご連絡した件ですが」）は結論の後ろに回すか削る。相手は結論を先に知りたい
- 変更点が複数あるなら番号つきの見出しで並べる。一つだけ「※」の注記に逃がすと、格下の情報に見えて見落とされる
- 依頼は末尾に【お願い】としてまとめ、希望日を書く。「目安を共有ください」だけだと返事が来にくい
- 敬語の段差をなくす。「お願いできますでしょうか」と「共有ください」が同じ文書にあると、丁寧さが揺れて見える

**依頼のテンプレート**

```
【依頼】〇〇のレビューをお願いします
- 対象: <リンク>
- 期限: 9/12 (金) 中
- 背景: △△のリリースに必要なため
```

## 設計書・仕様書

**読み手**: 実装者、レビュアー、数ヶ月後の自分。一意に解釈できることが最優先。

**文体**: 常体（だ・である、または体言止め）。

**構成**

- 目次を置き、見出しだけで設計の全体像（何を・なぜ・どう作るか）が伝わるようにする
- 冒頭に「目的」「スコープ（含む / 含まない）」「前提」を置く
- 決定事項と未決事項を分けて書く
- 判断の根拠を残す（「なぜこの方式にしたか」「検討して却下した案」）
- 用語定義を最初にまとめる。文書内で表記を固定する

**よくある失敗**

- 曖昧語で逃げる。「適宜」「基本的に」「必要に応じて」「など」は例外を隠す。例外があるなら例外を書く
- 主語が抜けて、誰が（どのコンポーネントが）行うのかわからない
- 「〜すべき」「〜が望ましい」が必須要件なのか推奨なのか区別できない。MUST / SHOULD / MAY 相当を決めて使い分ける
- 図が本文から参照されていない。図には番号か名前をつけ、本文で「図1 のとおり〜」と参照する。図・表・文の使い分けと Mermaid の型は `diagrams.md` にある

**表現の置き換え**

| 曖昧 | 明確 |
|---|---|
| 適宜リトライする | 最大3回、1秒間隔でリトライする |
| 十分な性能 | p95 レイテンシ 300ms 以下 |
| 基本的にはAを使う | Aを使う。ただし〇〇の場合のみBを使う |
| 〜など | （列挙を完結させるか、「以下に限定する」と書く） |

## メール

**読み手**: 社外または上長など、Slack より距離のある相手。

**文体**: 敬体。過剰な敬語は避ける。

**構成**

1. 件名で内容がわかる。「【要返信 9/12まで】〇〇の見積もりについて」
2. 宛名・簡潔な挨拶（1行）
3. 用件と依頼内容
4. 期限・背景
5. 結び（1行）

**よくある失敗**

- 件名が「ご連絡」「お願い」で中身が想像できない
- 「お忙しいところ恐縮ですが」「ご確認のほどよろしくお願いいたします」など定型句で本文の半分が埋まる
- 依頼が本文の最後にあり、途中で読むのをやめると伝わらない

## 用語解説・仕組みの説明

**読み手**: その用語を初めて聞いた人。または、知ってはいるが自分のコードでどう扱われるかを知りたい人。両方いるなら分けて書く。

**文体**: 敬体。

**構成**

1. 一文で「何か」を日常の言葉で言う
2. 数字を使った一つの例（「100万円入金して含み損20万円なら80万円」）
3. 例の各部分に用語を貼る
4. 式や関係。例の数字をそのまま使う
5. （必要なら線で区切って）自分のコード・テーブル・SQL での扱い

**よくある失敗**

- 用語が用語で定義されていて、最初の一文を理解するのに全部読む必要がある
- 同じものを「評価損益」「含み損益」「未実現損益」と呼び分け、読み手が違いを探す
- 「ざっくり」「だいたい」「≒」が重なり、正確にはどうなのかわからない。正の定義がどこにあるかを書く
- 一般解説とリポジトリの列名が同じ流れにあり、片方だけ読みたい人が止まれない

## 障害・CI失敗・不具合の説明

**読み手**: 影響を受けた人、または PR の作者。「自分のせいか」「何をすればいいか」を最初に知りたい。

**文体**: 敬体。

**構成**

1. 冒頭で「何が動いていて何が落ちたか」「読み手の変更と関係あるか」「まず何をするか」を言い切る
2. 原因を一つに絞り、見出しで言い切る（例: 「原因: サブモジュールのコミットをリモートが返さない」）
3. 根拠のログを、原因 → 結果の順で貼る
4. 対処を軽い順に番号で並べる
5. 補足として他の候補や条件を最後にまとめる

**よくある失敗**

- 因果の鎖が5〜6段あり、途中で「AかBかC」と枝分かれして犯人が決まらない
- 「条件」（shallow clone だった）と「原因」（取得が失敗した）が同じ重みで書かれている
- 最も軽い対処（再実行）が最後にあり、重い対処（設定変更）と同じ文に混ざっている
- 「自分のせいか」の答えが3番目の見出しにある

## README・ドキュメント（OSS・社内ツール）

**読み手**: 初めてリポジトリを開いた人。「これは何か」「どう動かすか」だけ知りたい。

**構成**

1. 一文で「何をするものか」
2. 動かすまでの最短手順（インストール → 実行）
3. よく使う使い方
4. 詳細（設定、構成、貢献方法）

**よくある失敗**

- 設計思想や経緯が先にあり、動かし方が下のほう
- 手順に前提（Node のバージョン、環境変数）が書かれていない
- コマンド例が実際には動かない（コピペで動く状態を保つ）

## 議事録

**読み手**: 欠席者と、あとから経緯を確認する人。

**構成**

1. 決定事項
2. TODO（担当・期限つき）
3. 議論の要点（誰が何を懸念したか）
4. 次回

**よくある失敗**

- 発言の時系列そのままで、何が決まったのか探さないとわからない
- TODO に担当者や期限がない
