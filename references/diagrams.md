# 図の書き方

設計書・仕様書・技術記事に図を入れるときに読む。図は原則 Mermaid で書き、本文と同じ Markdown に置く。図は本文の代わりではなく、本文の一文を目で追える形にしたもの。

## 1. 図にするか、表にするか、文にするか

図にするのは「流れ」「時間の前後」「状態遷移」「データ間の関係」だけ。それ以外は図にしない。

| 伝えたいこと | 使うもの |
|---|---|
| 複数の種別を観点ごとに比べる | 表。行に観点、列に種別 |
| 順番に実行する手順 | 番号つきリスト |
| 用語の定義 | 表。用語・意味・使用箇所 |
| どこからどこへ届くか | 図（flowchart LR） |
| 一つの処理の流れと分岐 | 図（flowchart TD） |
| 複数の主体が時間の中でどう絡むか | 図（sequenceDiagram） |
| テーブルやオブジェクトの関係 | 図（erDiagram） |
| 失敗と復旧の状態 | 図（stateDiagram-v2） |
| 時間軸の隙間、二つの経路の対比 | テキストの簡易図（`~~~text`） |

比較を図にすると、読み手は図の中から違いを探すことになる。表なら同じ行を左右に見るだけで済む。

## 2. 図を置く型

一つの図に一つのこと。全体像と個別の流れは別の図にする。

図の前後は次の形にする。

1. 見出し。図の主張を書く（「配信対象の登録と表示は別段階」）
2. リードの一文。図が何を示すかを言う
3. 図
4. 図の直後に「この図で言いたいこと」と「なぜそうするか」を一〜二文

図に載せた条件のうち本質的なもの（公開時刻の判定など）は、本文にも書く。図は読み飛ばされる前提で、文だけ読んでも筋が通るようにする。

同じ構造のものが複数あるなら（お知らせ、ポップアップ、通知など）、同じ形・同じ順の図を並べる。読み手は差分だけを見ればよくなる。逆に構造が違うもの（DB に対象行を作るものと、外部サービスに配信リストを渡すもの）は、無理に同じ形にしない。違うことが図の形から伝わるようにする。

## 3. 図の中の書き方

- ノードは役割で書く（「対象更新バッチ」「初回ログインAPI」）。本文にテーブル名やカラム名が出るなら、図でも同じ名前を使う。図と本文で呼び方を変えない
- 分岐は質問の形にし、「はい」「いいえ」で出す（`{現在時刻が publish_at 以降か}`）
- 矢印のラベルに条件や実行主体を書く（`-->|対象更新バッチ|`、`-->|publish_at を確認|`）。矢印だけでは「いつ」「誰が」が消える
- 全体像は左から右（LR）、一つの処理は上から下（TD）
- ノードは15個まで。超えるなら図を分ける
- sequenceDiagram の主体は短い別名（B、L、T）にし、表示名は本文と同じ日本語にする
- 一番大事な一点は `Note over` で示す。図の中で目が止まる場所を一つ作る
- 図の中に説明文を書かない。説明は図の外の本文に置く

## 4. 例

### 一つの処理の流れ（flowchart TD）

見出し「配信対象の登録と表示は別段階」の下に置く図。

~~~mermaid
flowchart TD
    A[記事が配信対象として確定] --> B[アカウント単位の対象行を作成]
    B --> C{現在時刻が publish_at 以降か}
    C -->|いいえ| D[対象行はあるが表示しない]
    C -->|はい| E{expire_at を過ぎているか}
    E -->|はい| F[表示しない]
    E -->|いいえ| G[一覧・詳細で表示]
~~~

図の直後: 公開前に対象行を作るのは、抽出後から公開前までに初回ログインしたユーザーを救済するため。表示側の publish_at 条件は残す。

### 複数の主体の時間関係（sequenceDiagram）

バッチと API が同じテーブルに書く順番と境界を示す。

~~~mermaid
sequenceDiagram
    participant B as 対象更新バッチ
    participant DB as 記事マスタ
    participant L as 初回ログインAPI
    participant T as 対象テーブル
    B->>DB: 基準時刻 T を保存
    B->>T: first_login_at < T の対象を登録
    L->>DB: T が確定済みの記事を取得
    L->>T: T <= first_login_at の対象を登録
    Note over L,T: 記事が公開前でも対象行を作る
~~~

図の直後: バッチは T より前、API は T 以降を担当する。境界が一つなので、どちらにも入らないユーザーが出ない。

### 時間軸の隙間（テキストの簡易図）

「なぜ漏れたか」のように、時間の間にある空白を見せたいときは Mermaid より縦のテキストが速い。

~~~text
T（抽出の基準時刻）
│
├─ バッチ抽出完了
│
├─ 初回ログイン
│  └─ 記事はまだ公開前
│
├─ publish_at
│  └─ 記事公開
│
└─ API は公開前の記事を見ない
   → 対象行が作られない
~~~

### 二つの経路の対比（テキストの簡易図）

構造が違うものを並べるときは、段下げで経路を書く。同じ形にしないことで、違いが形から伝わる。

~~~text
お知らせ
  記事
    → バッチまたは初回ログインAPI
    → 対象テーブル
    → アプリ表示

通知
  通知マスタ
    → バッチ実行時に対象抽出
    → CSV
    → 外部サービスに配信予約
    → OS 通知
~~~

## 5. よくある失敗

- 図だけ置いて本文がない。図は読み飛ばされるので、筋は文で通す
- 比較を図にする。表にする
- 一つの図に全体像と分岐と例外を詰める。分ける
- ノード名が本文と違う（図は「対象テーブル」、本文は「news_targets」）。揃える
- 矢印にラベルがなく、誰がいつ動かすのかわからない
- 図に番号や名前がなく、本文から参照できない。見出しかリードで指せるようにする
