# 文章の原則

SKILL.md の優先順位（読みやすさ → 簡潔さ → トーン → 自然さ）に沿って整理している。

## 1. 読みやすさ

### 構成

- 結論を先に書く。読み手は「結局どうなの」を最初に知りたい
- 見出しは内容の要約にする。「概要」「その他」より「移行前に確認すること」
- 見出しだけを拾い読みしても話の流れが追えるようにする
- 3つ以上の並列は箇条書きにする。ただし文章の途中で箇条書きが乱立すると逆に読みにくいので、段落で書けるものは段落で書く
- 同じ情報を二度書かない。確定情報（決定・スケジュール・数値）は先頭に一度だけ置く。個別の回答と全体の一覧が同じ内容を繰り返すと、読み手はどちらが正か照合させられる。繰り返す場所は差分（「前回から変わった点」）だけにする
- 並列の情報は並列の形にする。3つの変更点のうち1つだけ「※」の注記になっていると、読み手はそれを見落とすか、格下の情報だと思う

**目次と太字**

見出しが4つ以上、または1,500字以上なら目次を置く。目次は道しるべではなく要約として作る。見出しを「概要」「手順」「まとめ」のような分類ラベルにせず、その節の主張を一文で書く。

- 悪い目次: はじめに / 背景 / 方針 / 実装 / まとめ
- 良い目次: なぜ既存の認証を置き換えるのか / セッションからJWTへ移行する / 移行は3段階で旧方式と並走させる / 移行中に起きた問題と対処

目次を書いたら、上から読んで話が通るか確認する。通らなければ本文を書く前に見出しを直す。目次と本文の見出し・順序は一致させる。

太字も同じ発想で使う。必要なときだけ、ブロックにつき本質の一文を1つ。太字だけ拾い読みして話が通る状態にする。用語や名詞は太字にしない。要らなければ太字はゼロでよい。

### 原因や理由

障害の説明、設計判断の理由、レビューの指摘など「なぜ」を書くときは、本命を一つに絞って言い切る。因果の鎖は2段まで。鎖が長く枝分かれした説明は、読み手がどれが犯人か決められないまま最後まで読まされる。

- 悪い: shallow clone なので追加 fetch が走り、その途中でサブモジュール取得が失敗する。SHA が存在しないか辿れないか権限がないためで、SSH キーの差でも同じ症状になる
- 良い: 原因はサブモジュールのコミットをリモートが返さないこと。shallow clone はそれを表面化させた条件であって原因ではない

本命以外の候補は「補足」「他の可能性」として最後にまとめる。捨てるのではなく後ろに置くことで、本筋は一本のまま、漏れも防げる。「条件」と「原因」を分けて書くと、読み手が余計なものを犯人だと思わずに済む。

対処も同じ形にする。軽いものから順に番号で並べ、「まず再実行 → 続くなら設定変更 → それでも駄目なら全履歴取得」のように段階を示す。

### 段落

- 一段落一トピック。話題が変わったら段落を変える
- 段落の先頭文がその段落の要約になっている状態を目指す（先頭だけ読めば流れがわかる）
- 一段落は3〜5文が目安。長すぎたら分割、1文だけの段落が続くならまとめる

### 一文

- 一文一義。「〜で、〜ので、〜が、〜けど」で繋いだ文は分ける
- 60字前後を目安に、80字を超えたら分割を検討する
- 主語と述語を近づける。間に長い修飾が入るなら修飾を別文にする
- 各文はその場で意味が通るようにする。目的語のない述語（「効きます」＝何に？）、指す先が後ろの文にある指示語など、「次を読まないと分からない語」を残さない。読み手に前後の行を読み返させない
- 修飾語は修飾される語の直前に置く。「大きな赤いりんご」より「赤い大きなりんご」（長い修飾を先に）
- 読点は「意味の切れ目」と「誤読を防ぐ場所」に打つ。息継ぎの場所ではない

**例**

- 悪い: 「この機能はユーザーが登録時に入力した情報をもとに、管理者が承認した場合にのみ有効になるもので、承認前は利用できません。」
- 良い: 「この機能は、管理者の承認後にのみ有効になります。承認前は利用できません。判定には登録時にユーザーが入力した情報を使います。」

### 具体性

- 抽象語は具体例で補う。「パフォーマンスが向上」→「レスポンスが 800ms から 200ms に短縮」
- 用語を説明するときは、定義より先に具体例を出す。数字を使った一つの例を示し、そのあとで各部分に用語を貼る。用語を用語で定義すると、読み手はどこから読んでも足場がない
- 専門語を複数出さざるを得ないときも同じで、誰もが知る場面に置き換えて示す

**例: 用語の説明**

- 悪い: 有効証拠金は、預託証拠金に未決済建玉の評価損益を加減した額です。預託証拠金は入出金と確定損益を反映した残高です
- 良い: 100 万円を入金し、含み損が 20 万円あるとします。口座の実力は 80 万円で、これが有効証拠金です。入金した 100 万円のほうを預託証拠金と呼びます

悪い例は用語が用語を参照していて、最初の一文を理解するのに全部読む必要がある。良い例は一行目から足場がある。

**例: 専門語の言い換え**

- 悪い: 冪等性を保証するため、リトライ時に重複処理が起きないよう設計する
- 良い: 同じ注文ボタンを2回押しても注文が2件にならないようにする（これを冪等性という）
- 同じものを指す言葉を複数使わない。「評価損益」「含み損益」「未実現損益」のように言い換えが並ぶと、読み手は違いがあると思って止まる
- 「ざっくり」「だいたい」「≒」「イメージ」を重ねない。確信がないように見え、読み手は「正確にはどうなのか」と不安になる。正確に書けないなら、正の定義がどこにあるかを書く
- 「など」「等」「適宜」「基本的に」は仕様書では使わない。例外があるなら例外を書く

## 2. 簡潔さ

削っても意味が変わらない語は削る。以下は機械的に置き換えてよい。

### 冗長表現の一覧

| 冗長 | 簡潔 |
|---|---|
| することができる | できる |
| という | （削除、または「〜の」） |
| 〜ということになる | 〜になる |
| 〜において / 〜における | 〜で / 〜の |
| 〜に関して / 〜について | 〜は / 〜を |
| 〜を行う / 〜を実施する | （動詞にする）確認を行う → 確認する |
| 〜することが可能 | 〜できる |
| 〜する必要がある | 〜が必要 / 〜しなければならない |
| 〜と思われる / 〜と考えられる | 〜だ（根拠があるなら断定する） |
| 〜のような形で | 〜のように |
| 非常に / とても / 大変 | （削除。程度は数値で示す） |
| 基本的に / 原則として | （削除。例外があるなら例外を書く） |
| まず最初に | まず |
| 各々それぞれ | それぞれ |
| 事前に予約 | 予約 |
| 〜させていただく | 〜する / 〜します |

### 二重否定・回りくどい表現

- 「〜ないわけではない」→「〜する場合もある」
- 「〜しないことはない」→「〜する」
- 「〜ではないかと思います」→「〜だと思います」または「〜です」

### 前置きと結びの定型文

以下は情報を持たないので削る。

- 「以下に説明します」「〜について説明していきます」
- 「いかがでしたでしょうか」「参考になれば幸いです」
- 「ご存知の通り」「言うまでもなく」

## 3. トーンの統一

### 文体

- 一つの文書内で敬体と常体を混ぜない
- 箇条書きの中は体言止めか常体で揃える（本文が敬体でも可）
- 技術記事・Slack・メールは敬体、設計書・仕様書・コミットメッセージ・コード内コメントは常体が標準

### 表記の統一

- 用語: 同じ概念に同じ語を使う。「ユーザー / ユーザ」「サーバー / サーバ」「インターフェース / インタフェース」は文書内で片方に固定する（迷ったら長音符ありを推奨）
- 英数字: 半角に統一
- 括弧: 全角「（）」か半角「()」のどちらかに統一。日本語文中は全角が読みやすい
- 記号: 「：」「？」「！」は全角。ただし技術文書でコードや URL に隣接する場合は半角
- 漢字とひらがな: 「事」「時」「様」「頂く」「出来る」は補助的な用法ではひらがなにする（こと、とき、よう、いただく、できる）
- 送り仮名: 「行なう / 行う」「受け付け / 受付」など、文書内で統一する

### 敬語の程度

- 過剰な敬語は読みにくく、時に慇懃無礼になる。「〜させていただきます」は「〜します」で十分
- 社内向けは「です・ます」を基本にし、二重敬語（「拝見させていただく」「お伺いさせていただく」）は使わない

## 4. 自然な日本語

翻訳調・AI 調の特徴を消す。

### 翻訳調

- 無生物主語を避ける。「このライブラリはあなたに〜を可能にします」→「このライブラリを使うと〜できます」
- 「あなた」「私たち」など不要な人称代名詞を削る
- 「〜することを確実にする」→「必ず〜する」
- 「〜のうちの一つ」→「〜の一つ」または削除
- 受動態が続くなら能動態にする。「設定が管理者によって変更される」→「管理者が設定を変更する」

### AI 調

- 段落の頭で毎回「まず」「次に」「最後に」「また」「さらに」を使わない。順序は内容で示す
- 文末を「〜です。〜です。〜です。」で揃えない。「〜ます」「体言止め」「〜でしょう」を混ぜて単調さを避ける
- 「重要なのは」「注目すべきは」「ポイントは」で始めない。重要なら先に書けば伝わる
- 「〜することが重要です」「〜を心がけましょう」で締めない
- 太字は必要なときだけ、ブロックにつき1文まで。太字にするのは「主張の一文」であって用語や名詞ではない（「**有効証拠金**」ではなく「**含み損が増えると有効証拠金は減る**」）。太字だけを順に読んで要約になっていなければ、位置か文が間違っている。強調が要らない文章なら太字はゼロでよい
- 箇条書きの各項目を「**見出し**: 説明」の形で機械的に揃えない。必要なときだけ使う
- 網羅的に並べない。読み手に必要なものだけを書く

### 音読チェック

- 同じ助詞が連続する（「〜の〜の〜の」「〜を〜を」）→ 語順を変えるか分割する
- 同じ語尾が3回以上続く → 一つを別の形にする
- 読んでいてつかえる箇所 → 読み手もつかえる。書き換える
